# シフトSaaS 決定事項

2026-11-13 時点

## この文書の位置づけ

シフト自動作成SaaSで、これまでに確定した決定事項をまとめた正本です。Codexはこの文書を実装の基準に、Claude Codeは監査の基準にします。AIの説明文や会話の記憶を基準にしてはいけません。

**資料の優先順位**

1. この決定事項文書（`docs/decisions.md`。構成・体制・運用）
2. Hardルール定義書 v1.3（`docs/hard-rules.md`。Hardルール・用語・正解例の形式）
3. 企画・設計方針v0.2（業務の流れ、データモデル、ルールの考え方）

食い違いがあれば上位を優先し、下位の資料を直します。

## サービスとMVPの範囲

MVPは「希望収集 → 自動作成 → 管理者修正 → 公開」だけを、飲食・小売・サービス業の従業員5〜30人の事業所向けに作ります。

- 1つのコードベースと1つのシフトエンジンで、企業ごとの違いはRuleSet（設定データ）で表す。企業IDによるコード分岐は禁止
- シフトは数理最適化（OR-Tools CP-SAT）で作る。生成AIにシフトを作らせない
- 勤務パターン型。必要人数は30分単位の時間帯で定義する
- Hardルールは19個（H01〜H19）。法定時間外労働・法定休日労働を含むシフトは生成しない
- 提供形態はWeb／PWA。ネイティブアプリは作らない
- 打刻・給与計算・チャット・求人連携・シフト交換などは対象外
- 試作段階の目的は、維持費をかけずに、店長が作ったシフトより数値で優れることを示すこと

## 技術構成（②-2）

すべてCloudflareの既存のWorkers Paidプランの枠内で動かし、追加の固定費をかけません。テナント分離は、企業ごとにDurable Objectsを分けることで、データの保存構造そのもので守ります。

| 部品 | 使うもの | 役割 |
| --- | --- | --- |
| 画面・API | Cloudflare Workers（TypeScript） | 管理者・従業員の画面、業務API、Validator |
| 企業ごとのデータ | Durable Objects（SQLite）を企業ごとに1つ | 従業員、希望、RuleSet、シフトなど企業のデータすべて |
| 全社共通のデータ | D1 | ユーザー、企業への所属、認証 |
| 認証 | Better Auth（Workers上で動く公開ライブラリ）＋D1 | ログイン。ゼロからの自作はしない |
| Solver | Cloudflare Containers（Python＋OR-Tools CP-SAT） | シフトの自動作成 |
| メール | Cloudflare Email Service | 招待、締切・公開の通知 |
| バックアップ | 標準の復元機能＋R2への定期エクスポート | 障害・誤操作からの復旧 |

**守る原則**

- ブラウザから直接データベースを触らせない。すべてAPIを通す
- リクエストごとに、ログイン中のユーザーがその企業に所属しているかを照合してから、その企業のDurable Objectsだけを開く
- 自社のユーザーIDを主キーにし、認証ライブラリのIDは別に持つ
- シフトは版を持ち、生成結果は常に新しい下書き版として保存する。公開版を上書きしない
- ValidatorはTypeScript、SolverはPythonで別々に実装する
- 招待は従業員ごとの使い捨て・期限付きのQRまたはリンク。SMS認証は使わない

## アカウント・環境と反映方式

個人アカウントを開発・検証、会社アカウントを本番とし、コードは個人から会社への一方向だけに流します。反映は方式2（会社側の作業ブランチへpushし、PRで取り込む）＋GitHub Actionsによる自動デプロイです。

|  | 個人アカウント | 会社アカウント |
| --- | --- | --- |
| 使うPC | 開発PC | 会社PC |
| GitHub | Pro。開発の正本。Codexの実装、Claude Codeの監査、CI | Team。本番に出すコードだけを受け取る |
| Cloudflare | Paid。検証環境。合成データだけ | Paid。本番環境。実際の企業・従業員データはここだけ |
| AI | Codex・Claude Codeが扱う | AIは触れない |

**本番への反映手順**

1. タグを付ける前に、前回のタグ以降にマージされたPRがすべて、Claude Codeの監査を通り、ご本人がマージしたもの（PRの「merged by」がご本人）であることを確認する。違うものがあれば、Revertするか、監査してから進める
2. 個人GitHubで、Claude Codeの監査とCIを通った版にタグを付ける（例：v0.1.0）
3. 会社PCで、そのタグの版を取得し、会社リポジトリの反映用ブランチへpushする（手順書のコマンドを実行）
4. 会社GitHubでPRを作り、CIが通ったら画面で「Merge」を押す
5. mainへの取り込みを合図に、GitHub Actionsが会社Cloudflareへ自動でデプロイする

初回だけは、会社GitHubに空のリポジトリを作り、監査済みの版を履歴ごとpushします。

**守るルール**

- 会社側で直接コードを直さない。本番の緊急修正も、個人側で直して同じ手順で反映する
- 会社PCには、個人リポジトリを読むだけの権限（対象リポジトリ1つ、読み取り専用）を置く
- 会社CloudflareのAPIトークンは会社GitHubにだけ登録する。開発PCにも個人GitHubにも置かない
- 会社リポジトリのPRに承認必須は設定しない（本人しかいないため止まる）。CIの合格をマージの条件にする
- D1・Durable Objectsの識別子は環境別の設定に分け、コードに直接書かない
- Durable Objectsのデータ構造の変更は、検証で確認したものだけを、同じ順番で本番へ適用する
- 検証環境のメールは、事前に登録した宛先だけに送る

## 費用ゼロを守るための設定

枠を超えた分は自動で課金されるため、次の設定は個人・会社の両アカウントで必須です。

- Containersの同時起動数に上限を付ける。不具合で求解が繰り返し起動しても使用量が膨らまないようにする
- 求解が終わったらすぐコンテナを止める。待機中もメモリとディスクに課金されるため
- Cloudflareの使用量通知を設定し、枠に近づいた時点で気づけるようにする

**枠の共有に注意**

- 個人アカウントの枠（Containers、メール月3,000通、D1）は、求人サポートの開発と共有になる
- 会社アカウントの枠は別なので、検証での試行は本番に影響しない
- Solverの枠の目安：basic（1/4 vCPU・メモリ1GiB）なら1回1分で月約1,500回。足りる速さかはエンジン試作で確かめる

## 実装・監査体制と権限

実装はCodex、実装の監査はClaude Code、マージの判断はご本人が行います。AIが実装しAIが監査する体制なので、AIの権限を絞り、最後の判断を人に残します。

| 役割 | 担当 | 権限 |
| --- | --- | --- |
| 設計の監査 | ChatGPT（チャット） | なし（打ち切り規則に従う） |
| 実装 | Codex | 個人リポジトリへのブランチ作成とPR作成まで。マージ権限なし |
| 実装の監査 | Claude Code | 読み取りとレビューコメントだけ。マージ権限・本番の接続情報なし |
| マージ・承認・本番反映 | ご本人 | GitHubの画面で行う |

**監査依頼**

- Claude Codeへの監査依頼文は、まず毎回貼って使い、内容が固まったら `.claude/commands/audit-pr.md` に保存して `/audit-pr` で呼び出す
- 監査依頼文を `CLAUDE.md` には入れない
- 毎回必ず確認する項目：テナント分離（企業ごとのDurable Objectsを開く前の所属照合）、管理用の強い権限の使用、破壊的なデータ構造の変更、秘密情報の混入、正解例・形式定義の変更、ValidatorがSolverのコードを読み込んでいないか、テストが実装に合わせて緩められていないか

**正解例とCIの保護**

- 正解例（`golden/`）は、人間が承認した例でValidatorを縛る（案2）
- CIは「内容の検査」（常に合格が必要）と「保護対象の変更検知」（ご本人の確認後に採用）に分ける
- 保護対象：`golden/`、正解例の形式定義、例の読み込み・比較の処理、それを実行するCI設定、監査依頼文、`.claude/settings.json`
- Codexはご本人のアカウント名義で動くため、本人承認を技術的に完全には保証できない。AIのトークンにマージ権限を与えないことで補う
- テナント分離の自動テスト（他社のIDを指定しても届かないこと）は、最初からCIの必須項目にする

## セキュリティ

最優先は、ある会社のデータが別の会社から見えないことです。決定済みの対策は5つの層に分かれ、未決の項目は実証導入（実際の企業に使ってもらう）前に必ず決めます。

**決定済み**

| 層 | 対策 |
| --- | --- |
| 1. 会社同士のデータ分離 | 会社ごとにDurable Objectsを分け、書き間違いがあっても他社の保存場所に届かない構造にする。リクエストのたびに所属を照合してから、その会社の保存場所だけを開く。ブラウザからデータベースを直接触らせない。他社のIDを指定しても届かないことを確かめる自動テストを、最初からCIの必須項目にする |
| 2. ログイン | 公開ライブラリ（Better Auth）を使い自作しない。招待は従業員ごとの使い捨て・期限付きQRまたはリンクで、招待用の文字列はハッシュで保存する。全員共通の招待コードとSMS認証は使わない。退職者は「会社への所属」を無効にし、即時に効かせる。ある会社の管理者が、他社にも所属する人のログイン情報を再設定できないようにする |
| 3. 権限 | 管理者・シフト作成者・従業員の役割を分け、店舗ごとの範囲を持たせる。従業員は他人の希望休を見られない。契約・解約・データ削除は管理者のうちオーナーだけ。運営側の代理アクセスは会社内の役割と別にし、期限付き・原則読み取りのみ・全操作を記録する |
| 4. 個人情報を持ちすぎない | 希望休の理由は集めない。生年月日は持たず年齢区分だけを持つ。実際の企業・従業員データは会社のCloudflareにだけ置き、検証環境は架空データだけにする |
| 5. 開発・運用での事故防止 | AIは本番に触れない。会社CloudflareのトークンはGitHubの会社側にだけ置く。AIにマージ権限を与えず、mainをブランチ保護する。Claude Codeはpush・マージ・承認を禁止設定する。検証環境のメールは登録済みの宛先だけに送る。R2へ定期的にバックアップを書き出す |

**未決（実証導入の前に決める）**

試作段階では不要で、今決めなくても作り直しにはなりません。ただし、実際の企業に使ってもらう前には必ず必要です。

- 管理者アカウントの二段階認証
- APIの連続アクセス制限（総当たり攻撃の対策）
- 送信メールのなりすまし防止の設定（SPF・DKIM・DMARC）
- 監査ログに残す内容と保存期間
- 解約した会社のデータ削除と、従業員からの削除要求への対応（シフトの生成記録は氏名を外した形で残す）
- 共有端末でのログアウト時の処理（画面の保存データを消す）
- 障害の監視と、異常に気づく仕組み

## 設計監査の打ち切り規則

ChatGPTによる設計監査は、Hardルール定義書v1.3の差分監査（評価B、GO）で終了しています。監査が無限に続かないよう、以後は次の規則に従います。

- 判定がCONDITIONAL GOで新しいP0がなければ、再監査に出さずに次の作業へ進む。P1以下は、該当する作業を行うときに反映する
- ChatGPTの設計監査をやり直すのは、対応範囲を変えるとき、Hardルールを追加・削除するとき、社労士の確認で定義が変わるとき、技術構成を変えるときに限る
- 以後の確認は、実装のプルリクエスト単位でClaude Codeが行う
- 実店舗の勤務決定に使う前に、社労士の確認と対応範囲の確認を終える（定義書のとおり）
