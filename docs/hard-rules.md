# シフトSaaS Hardルール定義書 v1.3

Nov 13, 2026 · @magumatari

## この文書の位置づけ

MVPのHardルール19個と、その判定に使う定義・対応範囲を確定する文書です。正解例（Validatorを縛る人間承認済みの例）は、この定義書に従って作ります。

- 元になった資料：Hardルール案15個、ChatGPT設計監査（総合評価C、CONDITIONAL GO）
- 監査が求めた4条件（対応範囲、用語の定義、緩和と衝突の扱い、社労士確認の印）に対応する定義を定めます。未決事項と法令確認待ちの事項は区別して管理します
- 実装はCodex、監査はClaude Code。両者はこの文書を基準にし、説明文や会話の記憶を基準にしません
- 法令に関わる部分は社労士の確認前のため「暫定」です（社労士確認の節を参照）

## MVPの対応範囲

MVPは「通常の労働時間制度・法定時間外労働なし・法定休日労働なし・年少者の例外制度なし」の事業所だけを対象にします。対象外の条件に当たる企業・勤務は、法令違反ではなく「本製品の対応範囲外」として表示し、両者を同じ表示にしません。

**対象とするもの**

- 業種と規模：飲食・小売・サービス業、従業員5〜30人
- 時間モデル：勤務パターン型。必要人数は30分単位の時間帯で定義し、パターンの重なりで満たす
- 休日制度：毎週1日の休日
- 休憩：パターンに位置を固定して組み込む
- 兼務：同じ会社の他店舗での勤務だけを通算する
- 店舗間の移動時間：企業ごとに固定値1つ

**対象外（画面・規約で明示する）**

| 項目 | 扱い |
| --- | --- |
| 4週4休 | 対象外。毎週1休の事業所のみ受け入れる |
| 週44時間特例・変形労働時間制 | 対象外 |
| 法定時間外労働・法定休日労働を含むシフト | 生成しない |
| 他の会社での勤務（副業）の通算 | 対象外。通算していないことを明示する |
| 休憩時刻の自動配置 | 対象外。パターンに固定した休憩のみ |
| 中抜け勤務、同じ日の複数店舗勤務 | 対象外 |
| 店舗の組合せ別の移動時間 | 対象外。固定値1つのみ |
| 法令に基づく個別の就業制限（妊産婦など）の判定 | 判定しない。「勤務不可期間」として入力だけ受け付ける（H19） |
| 契約上の最低勤務日数・時間（旧H20） | MVPでは扱わない。実証導入時に追加を判断する |
| 扶養の判定 | 対象外。個人の上限時間として入力されたものだけ守る |

**対象外の条件が残る計画は公開しない（v1.1）**

対象外と表示するだけでは不十分なため、次の条件は確認状態を持ち、「条件あり」または「未確認」が残る計画は、19ルールすべてがPASSでも公開できません。

| 条件 | 確認状態 | 単位 |
| --- | --- | --- |
| 他の会社での勤務（労働時間の通算が必要なもの） | 該当なし確認済み／条件あり／未確認 | 従業員・対象期間 |
| 契約上の最低勤務日数・時間 | 該当なし確認済み／条件あり／未確認 | 従業員 |
| 法令に基づく配置義務（必要な資格者数など） | 該当なし確認済み／条件あり／未確認 | 店舗 |
| 入力で表現できない個別の就業制限 | 該当なし確認済み／条件あり／未確認 | 従業員・対象期間 |

導入時の手間を減らすため、企業単位で「該当者なし」を一括で確認できる入力を用意します。ただし一括確認は、その操作で示した従業員・店舗・期間にだけ適用します。後から追加された従業員・店舗や、条件が変わった契約には引き継がず、未確認に戻します。既存の「条件あり」を一括操作で「該当なし」に変えることはしません。確認者と確認日時を記録します。

**法定時間外労働の扱い（確定）**

成人を含め、この定義書の集計方法で実労働時間が1日480分または週2,400分を超える勤務は生成しません。これを超える法定時間外労働を組み込む必要がある運用は、MVPの対象外です。所定労働時間を超えるが法定の上限内の勤務は、法定時間外労働と区別し、入力された契約・企業・個人の条件に従います。

**年少者の範囲（v1.1）**

MVPの年少者は、最低就業年齢を満たした18歳未満の者に限ります。児童就労の例外制度は対象外です。

## 共通の用語定義

すべてのルール・Solver・Validator・正解例は、この定義に従います。定義にない解釈を実装で補ってはいけません。

| 用語 | 定義 |
| --- | --- |
| 時刻 | タイムゾーンは日本時間に固定。勤務は開始・終了の日時で持ち、時刻の大小から日跨ぎを推測しない |
| 時間の単位 | 整数の分。小数の時間で持たない。需要の30分単位と計算の単位は分ける |
| 区間 | 開始を含み終了を含まない［開始, 終了）。開始＜終了。端点が一致するだけの区間は重複としない |
| 勤務パターン | 勤務区間・労働区間・休憩区間・必要人数に数える区間を区別して持つ。版を持ち、変更は新しい版にする |
| 休憩 | パターンに位置を固定する。休憩区間は労働時間にも必要人数にも数えない |
| 労働時間 | 労働区間の合計（分）。有給・無給とは別の属性 |
| 被覆 | 時間帯の中のすべての時点で、実際に働いている異なる従業員数が必要人数以上であること。重なった人数では数えない |
| 1日（労働時間の判定） | 日跨ぎの連続勤務は、始業日の1勤務として扱う。午前0時で分割しない（暫定） |
| 1日（休日の判定） | 0時〜24時の暦日。前日からの勤務が0時を過ぎた日は休日に数えない（暫定） |
| 週 | 企業ごとに起算曜日を1つ固定する。生成のたびに変えない |
| 勤務日（連勤・勤務日数） | 勤務開始日で数える |
| 1勤務 | 同じ会社の中で、勤務開始日あたり1パターン |
| 生成期間 | 今回の生成で変更してよい範囲 |
| 集計期間 | 週・暦月など、上限を数える範囲。生成期間が月の途中からでも、月初からの既存勤務を含めて数える |
| 参照期間 | 連勤・禁止並び・既存勤務を確かめるため読み込む前後の範囲。前期間の勤務と、次期間の確定勤務を含む |
| 未入力 | 未入力の日を休日や0時間として扱わない。判定に必要な記録が欠けていれば「判定不能」 |
| 数値の設定 | 0以上の整数。「未設定」と「0」を区別する。下限≦上限 |
| 固定状態 | 未固定／勤務固定／休み固定の3種類。勤務固定は従業員・店舗・日時・パターンの版を特定する |
| 年齢区分 | 成人／年少者／未確認の3種類。適用開始・終了日、確認者、確認日を持つ。生年月日は持たない。未確認を成人として扱わない |
| 全設定共通 | 根拠、適用対象、適用期間、単位、緩和区分、版を持つ。月の途中で設定を変えても過去の判定を書き換えない |

### 期間・区間・状態の追加定義（v1.1）

再監査（評価B）を受けて追加した定義です。上の表と食い違う場合は、この表を優先します。

| 項目 | 定義 |
| --- | --- |
| 翌期間の扱い | 翌期間は同時に生成しない。各上限の残りの枠と、月末で切れた週の休日確保の条件を保存し、次の生成と手修正で必ず守る |
| 労働時間の帰属 | 日・週・月とも、勤務の労働時間の全量を勤務開始日に帰属させる（法令確認待ちの暫定） |
| 連勤の参照範囲 | 最大N連勤の確認には、生成期間の前後それぞれN日分のうち、過去の予定と確定済みの未来勤務を読み込む。翌期間の未計画日を休日として扱わず、それだけを理由に判定不能にもしない。期間末の連勤数を保存し、次の生成・手修正では引継ぎ元の予定を含めて検証する |
| 月・期間の上限の集計 | 同じ会社の全店舗の勤務を、同じ従業員について合計する。生成期間外の同月の勤務も含める |
| 予定と実績 | MVPは打刻を扱わないため、予定だけを使う。同じ勤務を二重に数えない |
| 記録の欠け | 判定に必要な過去・既存の勤務記録がない状態。判定不能とする |
| 未計画 | 今回の生成で決める日。記録の欠けとは別に扱う |
| 休日 | 勤務区間が1分もない暦日で、休暇でない日。今回の生成で勤務なしと決まった日も含む |
| 休暇 | 年休など。勤務は入れないが、休日には数えない |
| 休み固定 | 従業員と暦日を指定する。同じ会社の全店舗で、その暦日の0時〜24時に勤務区間が重なる割当を禁止する。前日開始の勤務の食い込みも禁止する。MVPは日単位のみ |
| 被覆区間 | 必要人数に数える区間。H04・H05はこの区間で数える。研修など、労働でも人数に数えない時間がある |
| 勤務パターンの整合 | 被覆区間は労働区間の内側。労働区間と休憩区間は重ならない。両方とも勤務区間の内側。勤務区間に未分類の時間を残さない。登録時に検査する |
| 期間上限の変更 | 次の集計期間から適用する。期間の途中では変えない |
| 再生成の範囲 | MVPは店舗単位・生成期間全体の再生成だけを提供する。部分的な再生成はしない |
| 未設定の値 | 兼務可否、休息時間、移動時間などの未設定を、「兼務可」「0分」に自動で置き換えない。正解例ではすべての設定値を明示する |

**入力の規則（Hardではない）**

- 希望休の提出上限：期間あたりの日数で数える。上限を超えた提出は明示的に拒否し、黙って削除しない。画面だけでなくAPIとCSV取込でも同じ規則で検査する
- 確定休暇・勤務不可期間（H19）は、希望休の上限の対象外
- 年齢区分が「未確認」の人は、H18により配置しない

## 緩和区分と衝突時の処理

不足診断で緩めてよいのはH04とH05だけです。それ以外のHardは、Solverが自動で緩めたり、黙って固定を解除したりしてはいけません。

| 緩和区分 | 対象 | 扱い |
| --- | --- | --- |
| 不足診断で緩和可 | H04、H05 | 不足の日時・人数・スキルを表示する。結果は仮シフトとし、公開不可 |
| 条件変更で比較 | H06、H07、H08、H10 | 元の設定は変えず、「この条件を変えた場合」として別に計算する |
| 明示的な変更が必要 | H11、H13、H14、H15 | 固定の解除や条件の変更を人が行った後、新しい入力の版で再計算する |
| 緩和しない | H01〜H03、H09、H12、H16〜H19 | 違反する仮シフトも作らない |

**生成できないときの処理順**

1. 入力の段階で、固定同士・固定と勤務不可・固定と確定休暇の衝突を検出し、生成前に表示する
2. 全Hardを守って生成を試みる
3. 解けなければ、H04・H05の不足だけを許して診断する
4. それでも解けなければ、固定・勤務不可・契約条件などの衝突を表示する
5. 人が条件を変更した後、新しい入力の版で再生成する

**Solverの状態ごとの処理（v1.1）**

上の処理順の「解けなければ」は、次の状態で分岐します。不足診断側のSolverにも同じ区別を適用します。

| Solverの状態 | 処理 |
| --- | --- |
| 実行不可能（INFEASIBLE） | 元のHardでは成立しないと確定。H04・H05の不足診断へ進む |
| 判定未確定（UNKNOWN） | 時間制限その他の理由で可否を確定できなかった状態。停止理由を別に記録し、人員不足や衝突と断定しない |
| モデル不正（MODEL\_INVALID） | システムの不具合として扱い、業務上の不足とは分ける |
| 実行可能（FEASIBLE） | 候補をValidatorへ渡す。最適性が未証明であることを保持する |
| 最適（OPTIMAL） | 候補をValidatorへ渡す。状態だけで公開しない |

**不足診断の単位**

- 不足量は「人数×分」で表す
- 人数の不足（H04）を、スキル・役割の不足（H05）より先に評価する
- 不足診断は、Softの最適化より前に行う

**守ること**

- 「必ず仮シフトを返す」ことを仕様にしない。衝突を返すべき場合がある
- 不足人数を「あと何人採用すればよい」と言い換えない。人数不足と技能不足は同じ1人で解消する場合がある
- Solverの状態は、実行不可能・判定未確定・モデル不正・実行可能（最適性未証明）・最適を区別して保存する。判定未確定を「人員不足」と表示しない

## Validatorの判定条件

シフトを公開できるのは、同じ入力の版に対して、ValidatorがH01〜H19すべてをPASSと判定した場合だけです。Solverの状態が「最適」でも、それだけでは公開できません。

**結果の区分**

- PASS：満たしている
- FAIL：違反がある。違反したルールID、日時、従業員、実測値、上限値、差分を返す
- 判定不能：履歴の欠け、年齢区分の未確認など、判定に必要な記録がない。PASSとして扱わない

**独立性（案2の条件）**

- ValidatorはSolverのコードを読み込まない。CIで機械的に検査する
- Solverが計算した被覆表や労働時間を使わず、元の日時・休憩・履歴から計算し直す
- 実装言語は、SolverがPython、ValidatorがTypeScript

**再検証が必要になる場面**

- 手動修正、必要人数の変更、資格の変更、兼務先の勤務の更新、公開の直前
- 更新後は、それ以前のPASSを無効にする
- 公開の経路（画面、API、従業員への配信）はすべて、検証済みの版だけを公開できる

**正解例の組の中身**

- 適用するルールの版、入力、シフト、期待する結果（PASS／FAIL／判定不能）、違反ID、違反量
- 同じ程度に良い解が複数ある場合、特定の1枚だけを正解としない

**検証と公開の対象（v1.1）**

- 検証結果は、入力・割当・ルール・参照した他店舗の勤務の版の組に結び付ける
- 検証した割当と公開する割当が完全に一致する場合だけ公開できる
- 2店舗の確定が同時に起きた場合、確定時にも他店舗の勤務の版を確認し、変わっていれば再検証する。確認から確定までの間に別の変更が入った場合は、一方の確定を通さず再検証する（公開処理の受入試験で確認する）

**正解例の状態（v1.1）**

| 状態 | 意味 | CIでの扱い |
| --- | --- | --- |
| 仕様確定 | 判定規則が決まり、人間が期待結果を承認した | 通常の期待結果として使う |
| 法令確認待ちの暫定 | 判定規則と期待結果は決まったが、社労士の確認が未了 | 暫定と明示して使う。法令に適合した証明とは扱わない |
| 仕様未決 | 判定規則が決まっていない | 合否の期待結果を登録しない。未決の件数と対象を表示する |

- 実行時の「判定不能」（規則は決まっているが記録がない）と、正解例の「仕様未決」（規則が決まっていない）は別物
- 期間境界の正解例は、当期の判定結果・保存する引継ぎ条件・次期で許される操作を1組にする。正解例ごとに、期待結果が何に依存しているか（どの定義・法令解釈か）を記録する
- 正解例は「ルール単体の例」か「全Hardを検証する統合例」かを明示する。例えば労働481分・休憩60分は、H16単体ではPASS、統合ではH17違反でFAIL

## 社労士確認と「暫定」の印

法令に関わる正解例は、社労士の確認を受けるまで「暫定」の印を付け、確定した正解として扱いません。確認は、試作段階では行わず、実証導入の前に受けます。

**暫定の印の扱い**

- 対象：H01、H02、H03、H16、H17、H18の最低就業年齢、H19に入力する法令由来の制限、用語定義の「1日」の2項目と労働時間の帰属、確定シフト変更の手続。H番号で機械的に決めず、正解例ごとに依存する定義で判断する
- 暫定の正解例もCIで使うが、確認後に期待結果が変わる可能性があることを記録する
- 確認後に期待結果が変わった場合は、正解例の版を上げ、変更理由を残す

**実店舗で使う前の条件（v1.1）**

暫定ルールでのCI成功とValidatorのPASSは、暫定の定義と一致していることを示すだけです。実店舗の勤務を決めるのに使う前に、社労士の確認と対応範囲の確認を終えます。対象外の条件が残る計画は、19ルールすべてがPASSでも確定公開しません。架空データや過去シフトとの比較検証は、この確認の前に行って構いません。

**社労士に確認する事項**

1. 対応範囲：通常の労働時間制度に限り、特例・変形労働時間制・時間外労働・休日労働を対象外とすることの表示方法
2. 休日の判定：週の起算、暦日での判定、日跨ぎ勤務、年休との区別
3. 日跨ぎ・週跨ぎの集計：始業日の1勤務として扱う方法、週の所属
4. 年齢区分：適用の時点、最低就業年齢の確認、事業場の年齢証明とSaaS側の記録の役割分担
5. 休憩：パターンに固定する方法、分割の可否、自由利用の扱い
6. 個別の就業制限：妊産婦・育児介護などを「勤務不可期間」の入力だけで扱うことの妥当性
7. 確定後の変更：確定したシフトを変更する手続と、固定解除の権限の分け方

## 正解例の形式

正解例は、JSONで1ファイル1例とし、各ファイルだけで入力から期待結果までが完結する形にします。Validatorを縛るための形式で、Solverの試験の形式は別に定めます。この節の記載が食い違う場合は、後半の「形式の規約（v1.3）」を優先します。

**基本方針**

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 書式 | JSON | PythonとTypeScriptの両方が追加の部品なしで読める。YAMLは時刻や「NO」を別の値に読み替える古い仕様があり、事故の元になる |
| 単位 | 1ファイル1例 | 差分が見やすく、どの例が変わったかを監査しやすい |
| 中身 | 各ファイルで完結 | 共通データを参照すると、参照先の変更が多数の例に黙って波及する。対象ルールを検証できる最小の人数・期間を目安とし、必要なら店舗・期間を広げる |
| 置き場所 | `golden/` フォルダ | 内容の検査は常に合格が必要。保護対象の変更は、ご本人の確認後に採用する |
| 形式の検査 | JSON Schemaで全ファイルを機械検査 | 形式定義ファイルも保護対象にする |
| キー名 | 英語 | タイトル・説明・依存する定義は日本語 |

**1つの例に持たせる項目**

| 区分 | 項目 |
| --- | --- |
| 管理情報 | `id`、`title`、`definition_version`、`schema_version、status`、`kind`、`target_rules`、`depends_on`、`approved_by`、`approved_at`、期間境界の例は `group_id` |
| 入力（`input`） | 企業設定（すべての値を明示）、店舗、従業員（年齢区分・在籍期間・資格）、勤務パターン、必要人数、希望休、固定、既存勤務、前期からの引継ぎ、対象外条件の確認状態 |
| 検証するシフト（`assignments`） | 従業員、店舗、パターン（`ID@版`）、勤務開始日 |
| 期待結果（`expected`） | `result`（PASS／FAIL／INDETERMINATE）、FAILなら違反ごとに違反コード・対象・区間と、数量比較がある場合だけ実測値・上限値・比較・差分・単位、判定不能なら理由、期間境界の例は次期へ引き継ぐ内容 |

**状態と種類**

- `status`：`draft`（下書き）／`confirmed`（仕様確定）／`provisional_legal`（法令確認待ち）／`undecided`（仕様未決）
- 下書きはCodexが作ってよい。形式の検査は行うが、正式な期待結果の照合には使わない。下書きから他の状態へ変えるのはご本人だけ
- `undecided` は合否の期待結果を持たない
- `kind`：`unit`（対象ルールだけ判定）／`integrated`（19ルールすべて判定）

**時刻の書き方**

- 日時は日本時間で `2026-12-01T22:00` のように書き、時差の表記は付けない
- 勤務パターンは開始時刻と、開始からの分数の区間で表す。22:00開始の夜勤なら、労働 `[0, 240)`、休憩 `[240, 300)` のように書き、0時をまたいでも数字が逆転しない
- 時間の長さはすべて整数の分

**期間境界の例**

当期と次期を、同じ `group_id` の2ファイルにします。次期ファイルは、当期ファイルが期待する引継ぎ内容をそのまま入力に使います。保存した引継ぎが次期で使われない不具合を検出するためです。

**形式の規約（v1.3：形式監査の反映）**

違反の表し方

- 違反は、`rule`、違反コード `code`、対象（従業員・店舗・役割・割当ID・固定IDのうち、そのコードで必須のもの）、区間または期間で表す
- 数量の比較がある違反だけ、`measured`、`limit`、`comparison`（上限は `<=`、下限は `>=`）、`diff`、`unit`（`minutes`／`days`／`people`／`assignments`）を持つ。`diff` は常に `measured − limit` で、負の数を許す
- 違反コードごとに必須の項目を固定する（例：`REST_SHORTAGE` は従業員と前後の割当ID、`STAFF_SHORTAGE` は店舗・区間・人数）

期待結果との照合

- 期待する違反と実際の違反を、過不足なく照合する。順序は問わない。同じ違反の重複はエラーにする
- 数値・日時は正規化してから厳密に一致させる。説明文は照合しない
- H04・H05は、対象・コード・値が同じ隣接区間を1件に結合してから照合する
- 結果はルールごとに持つ。`unit` は `target_rules` のルールを、`integrated` はH01〜H19のすべてを評価し、実際に評価したルールの一覧も照合する
- 全体の結果：確定した違反が1件以上ならFAIL、違反はないが判定できないルールがあればINDETERMINATE、すべて適合ならPASS。FAILでも判定不能の理由は残す
- 判定不能の理由は、理由コード・対象ルール・対象従業員・欠けた記録の種類と期間で表す

入力の範囲と完全性

- `coverage` で、検証する期間、候補の割当が全量である範囲、既存の勤務記録がそろっている範囲（従業員・期間）を明示する。記録の欠けとするのは、判定に必要な過去の予定・確定済み勤務について、完全性を確認できない範囲だけとする。翌期間の未計画は記録の欠けと区別し、それだけを理由に判定不能にしない
- 割当には一意の `id` を付ける。担当役割を検査する例では、役割と区間も割当に持たせる
- 項目ごとに「キーなし・null・0」の意味を定める。対象ルールに関係する設定は、該当なしでも空配列などで明示する。省略した項目を0や許可に置き換えない

承認

- `confirmed` と `provisional_legal` は、`approved_by`・`approved_at`・期待結果を必須にする。`undecided` は合否の期待結果を持たない
- 承認の対象は例全体（入力・対象ルール・種類・依存する定義・版・期待結果）。意味が変わったら `draft` に戻して再承認する
- `provisional_legal` の承認は、暫定の定義から期待結果が導けることの承認で、社労士確認済みの意味ではない
- JSONの状態値だけでは本人の承認を保証できない。CodexとClaude Codeが使うトークンにはマージ権限を与えず、マージはご本人がGitHubの画面で行う
- CIは「内容の検査」（形式・参照・期待結果との一致。常に合格が必要）と「保護対象の変更検知」（ご本人の確認後に採用）に分ける。保護対象は、`golden/`、形式定義ファイル、例の読み込み・比較の処理、それを実行するCI設定

その他

- `schema_version`（形式の版）を `definition_version` と別に持つ
- 勤務パターンは `duration_minutes` を持ち、労働区間と休憩区間で勤務区間全体を過不足なく覆う
- 日時はすべて日本時間として解析し、実行環境のタイムゾーンに依存させない。`24:00` は使わず翌日 `00:00` とする。実在しない日付は拒否する
- 例の大きさは「対象ルールを検証できる最小の人数・期間」を目安とし、必要なら店舗や期間を広げてよい
- この形式はHardルールの判定だけを扱う。対象外条件による公開可否は、公開処理の試験で別に検査する
- 期間境界の例は、前の例のIDで前後関係を示す。期待引継ぎと次期入力の一致に加え、実際の引継ぎ処理の出力も照合する
- JSONの重複キーは読み込み時に拒否する。Hardに違反する入力そのもの（481分の勤務など）は形式上は正しいデータとして受け付ける
- 期待値を、Validatorの出力で一括上書きして承認済みにしない。複雑な数量には `derivation` に導出を短く書く
